## Overview

這篇論文主要是探索 PIM (Process-In-Memory) 晶片可以如何解決現有的問題。

最大的貢獻價值在於發現 vector similarity search 的其中一個解法 IVF 的特性很適合 NMP 硬體（一種 PIM 硬體），並利用 UPMEM（已商業化的 NMP 晶片）成功使得了 IVF 不再 bounded by memory bandwidth。


## 問題情境 - Vector Similarity Search

給定一個 query vector $q$，輸出 top-k 與 $q$ 最接近的 vectors。

最接近的定義可以是 euclidean distance (L2) 或是夾角最小 aka. cosine 值最大。

### Vector Similarity Search 的實作方法

<InfoBox>
Exact search (kNN)：資料量太多、vector 維度太大，暴力枚舉所有的 vector 算距離 infeasible（在這裡不知道需不需要提及資料的規模）
</InfoBox>

<InfoBox>
ANN (Approximate Nearest Neighbor)：找近似的 top-k。方法有 Tree-based、Hash-based、Graph-based、IVF (Inverted File Index)。
</InfoBox>

- Hash-based：vector 數量變多時，精度會變非常差。
- Tree-based：vector 維度變高時，效率退化至接近暴力。
- Graph-based：vector 數量、維度規模變大時，DRAM consumption 非常大。

這裡暫不考慮上述方法。


## Background

### IVF (Inverted File Index)

Preprocessing Phase：
1. database vectors 用 k-means (在這裡 k-means 的 k 稱作 `nlist`​) 找 centroids、切成 `nlist​` 個 clusters。
2. 建 Inverted file list：將每個 database vector 歸類到最近的 centroid 管轄的 cluster。

Querying Phase，當給定 query vector $q$ 時：
1. 找前 nprobe​ 個與 $q$ 最近的 centroids。
2. 枚舉這些 centroids 管轄的 clusters 內所有 vectors，算距離，最後排序排出 top-k。


### NMP (Near-Memory Processing)

- PIM (Process-in-memory) 的一種類型。
- Places computing units closer to memory units.
- UPMEM: The first commercially available off-the-shelf NMP device.



### UPMEM

通用架構（搭配 Fig. 2）：

每個 DPU 內部：RISC core（14-stage pipeline）、24 tasklets、IRAM 24KB / WRAM 64KB / MRAM 64MB
DPU 之間 MRAM 不共享，無法直接通訊
Host 透過 Transfer API 搬資料、Control API 發指令



## Observation


### IVF search phase is memory-bound

論文做了實驗證明 IVF search phase (以 FAISS 爲測試用 library) 是 memory-bound。

1. 跑 FAISS-IVF
    - CPU：Intel i7-12700
    - DRAM：128 GB DDR5
    - DRAM 理論 bandwidth：59 GB/s
    - 用 Intel VTune profile。
2. 增加 CPU threads
    - 1, 2, 4, 8, 16 threads
    - 看 search time、CPI、load latency、DRAM bandwidth。
3. Observations：
    - 8 threads 後 saturates（search time 幾乎不再降低）
    - CPI 隨 threads 增加而上升，且超過 1。
    - load latency 隨 threads 增加而上升。
    - DRAM bandwidth 到 8 threads 左右接近理論峰值。

多 threads 沒辦法繼續加速 $\rightarrow$ shared DRAM bus 被打滿 $\rightarrow$ CPU idle $\rightarrow$ FAISS-IVF search phase 是 memory-bound。


### IVF search phase has an affinity for UPMEM.

IVF search 的 distance calculation 天然可平行——每個 vector 的距離計算互相獨立，不需要 synchronization，正好對應 DPU 之間無法互相通訊的限制。

搬過去的資料 (query metadata) 與搬回來的資料很小——DPU 算完只回傳 ⟨ID, dist⟩ pair（8 bytes），不用把整個 vector 搬回 host，大幅減少 shared bus 的壓力。




## UPVSS Components


### DPU-aware Cluster Partition

解決的問題：每個 IVF cluster 可能超過單一 DPU 的 64 MB 限制，而且要平均所有 DPU 的負擔。
做法：把每個 cluster 的 vectors 平均切成 N 份（N = DPU 總數），每個 DPU 拿到每個 cluster 的一小段。

效果：
- 不會 OOM（每份夠小）
- 任何 query 不管命中哪些 clusters，所有 DPU 都會被啟動 → 充分利用 aggregate bandwidth
- 每個 DPU 獨立算，不需要 inter-DPU synchronization




### DPU-aware Vector Similarity Search Coordinator

解決的問題：怎麼協調 host CPU 和 DPU 的分工，以及怎麼用好 DPU 內部的 WRAM。


Host side 流程：
1. 收到 query vector，找出 nprobe 個最近的 centroids → 組成 Query Metadata
2. 把 Query Metadata broadcast 給所有 DPU
3. 發指令讓 DPU 開始算距離
4. 收回每個 DPU 回傳的 ⟨ID, dist⟩ pairs
5. Merge 所有 partial results → 最終 top-k

DPU side 流程（WRAM 記憶體管理）：
1. Query Cache（WRAM）：存 Query Metadata，所有 tasklet 共享
2. Vector Cache（每個 tasklet 各 2 KB WRAM）：各 tasklet 獨立搬自己負責的 vectors 進來算
3. 算完的 ⟨ID, dist⟩ 寫入共享的 Key-Value Pairs Cache（2 KB WRAM）
4. 一個 key-value pair 大小 8 bytes。Cache 滿（256 對）時，指定一個 tasklet 負責 flush 回 MRAM

## Appendix

### Graph-based v.s. IVF (Inverted File Index)

Graph-based 與 IVF 雖然都適合大資料集，但實際上兩者都會有兩個瓶頸：DRAM capacity 與 DRAM bandwidth。而這篇論文雖然沒解決 DRAM capacity 的問題，但卻洞見了 IVF 可以結合 PIM 硬體從而解決 DRAM bandwidth 的問題。

<Table>
| 方法          | DRAM Capacity Issue                           | DRAM Bandwidth Issue                                  |
| ----------- | ------------------------------------------ | -------------------------------------------------------------------- |
| Graph-based | 存 neighbor links / graph metadata，空間複雜度還行但常數非常大，並且圖的存取是 random access，必須把整張圖載入 DRAM 否則會一直發生 page fault | random access 會造成一堆 cache misses   |
| IVF         | 以這篇論文的實驗方法來說，database vectors 也要能完整塞入 DRAM  | search phase 掃大量 vectors，每個 vector 載入 cache 只用一次就 flush，reuse rate 極低 |
</Table>


<Table>
| 方法   | DRAM Capacity Solution                    | DRAM bandwidth Solution                             |
| ----------- | ------------------------------------------ | -------------------------------------------------------------------- |
| Graph-based | - | - |
| IVF         | Product Quantization  | UPVSS |

### UPMEM 的 DPU

DPU 的架構是 (FGMT) Fine-Grained Multithreading，有 24 條硬體執行緒（稱作 tasklets）。

DPU 的 pipeline stages 有 14 階，最大內部指令的延遲爲 RAW / branch，爲 11 cycles，沒有 forwarding / early branch hardware，因此如果要確保 pipeline 使用率 100%，至少要開 11 個 tasklets 並且中間不能 stall。或者如果要隱藏時間長得多的「MRAM 存取延遲 (DMA Latency)」，通常需要將 tasklets 數量開到滿（例如 16 到 24 個），並且配合較大的單次 DMA 傳輸區塊大小（例如大於 256 bytes），才能 saturates DPU 的運算效能。

DPU 的 tasklets 是按照 Round-robin 的 policy 塞指令進 pipeline。每輪都會循環地尋找下一個 ready 的 tasklet（tasklet 的狀態有可能是 stall，例如發起 DMA request）。Round-robin 是在硬體層面實作的（仲裁器 / Arbiter）。
